# Implementation Status

## Live detection on Missions (23 October 2026)

Added `POST /api/v1/drones/live-detect` and a **Live detection** panel on the Missions screen. The browser samples a camera or a local video file at about 2 frames a second (640 px JPEG), sends one frame at a time to the same local YOLO adapter used for uploads, and draws the returned boxes. Responses are labelled `IMPORTED`; every box is `UNCERTAIN` and a candidate container only. Frames are analysed and discarded: no media row, finding or audit event is written. "Save frame for ground review" sends the current frame through the existing `POST /media` path, which creates the usual `UNCERTAIN` findings. No migration. The checkpoint hash is now cached per process (`_checkpoint_digest`), because it was previously recomputed on every inference call.

- Tests: `services/api/tests/test_live_detect.py` (5 passed; calls the route function directly, model stubbed). `npm run typecheck` passes; `npm run lint` has no errors (one existing warning in `township-scene.tsx`).
- HTTP check against a scratch API (throwaway SQLite, real drone checkpoint, operator login): an egg photo (`NO_DETECTIONS`) and a held-out drone tile both returned 200; the tile gave one `water_tank` at 0.88 confidence, `UNCERTAIN`, `persisted: false`; no media row was added (only the 8 seeded fixtures); no cookie gave 401. The first call took about 22 s (model load), later calls about 0.4 s on CPU. The API must be restarted to load the new route.
- Not verified: the panel has not been run in a browser, so camera permission, the overlay alignment and the real-checkpoint frame rate are untested. There is no Playwright spec yet.
- Limits: CPU YOLOv8n speed on this machine is unmeasured. Frames come from the user's own camera or a file, not from a drone link, and there is no tracking across frames, so the same container can be a new box each frame. The endpoint has no per-user rate limit; the client loop is sequential, but another client could call it faster.

## Allocation benchmark review (23 October 2026)

Finding: the first benchmark could not show any benefit. Each policy could add only one extra task per block, so budgets above 10 staff hours were never spent, and the adaptive policy gave block 1 (3 unresolved sources and a recurring asset) a single task. Adaptive and uniform tied at 4 of 8 scripted issues at every budget from 4 to 16 hours.

Change (`allocation_benchmark.py`): every policy now spends its whole staff budget. Uniform and static keep cycling their fixed inspection order (never inspecting offline blocks). Adaptive builds a queue from evidence only: recurrence review (weight 6), each unresolved verified source (weight 5), then extra inspections ranked by egg signal with diminishing returns. Scenario truth still never reaches a policy (tested). The result now includes a `budget_sweep` (4 to 16 hours), shown on the planning screen and in the exported Markdown.

Result, scripted scenario only: at 8 hours uniform 4/8, static 3/8, adaptive 5/8; adaptive reaches 7/8 at 12 hours and 8/8 at 16, while uniform and static plateau at 4/8 because they never schedule removal or recurrence work. All three tie at 4 hours (reserved coverage only). Read this as "a policy that acts on known open work covers more of the scripted issues than one that only patrols", not as an effect size: the verified-source and recurrence labels correspond to facts the evidence also states, so only the latent-site discovery is a genuine test of the policy.

Open issues: (1) the scripted truth omits block 4's unresolved verified source although the fixture and seed list one (this lowers adaptive's score if anything, and was left unchanged to avoid tuning the labels); (2) the benchmark's adaptive policy is separate from the production planner in `planning.py`, which proposes one task per block and never `ENGINEERING_REVIEW`, so this result does not yet test the shipped rules; (3) baseline policies never schedule source removal by design.

| Staff hours | uniform | static | planner_v1 | adaptive |
|---:|---:|---:|---:|---:|
| 4 | 3 | 3 | 2 | 3 |
| 8 | 4 | 3 | 4 | 5 |
| 12 | 4 | 4 | 4 | 7 |

What this says about the shipped planner: it ties routine uniform inspection at 8 hours and trails it at 4, so the benchmark does **not** support a claim that the current planner beats equal allocation. At 4 hours the planner spends the offline block's reserved hour on an inspection rather than servicing the trap. It also does not schedule recurrence reviews; those are created separately as work orders by the referral rule and are outside the planned hours. Only the proposed adaptive policy leads, and its lead comes from scheduling known open work.

The work queue on Field operations now defaults to a board with five columns that follow the persisted state machine: To assign (OPEN, REOPENED), Assigned, In progress, Action recorded, Verified resolved. "Action recorded" (ACTION_COMPLETED_PENDING_VERIFICATION) is a separate, dashed column labelled as not yet verified, so a recorded action is never shown as a result. Cards show block, asset, reason, age and assignee, with badges for REOPENED and RECURRENCE (engineering review). A search box and block and task-type filters apply to both the board and the previous list view. The same buttons, roles and API calls are used as before (one shared `WorkActions` component); no API or schema change.

Checked in a browser with a fresh database across three roles: a coordinator approved a plan (8 tasks in To assign) and assigned one, the inspector started it and recorded the action, an independent reviewer verified it, and the card moved through each column; searching "block-4" filtered to two tasks. Only inspectors can start or complete, only reviewers can verify, and the API still refuses the same person completing and verifying.

Known gaps: the existing Playwright spec `closed-loop.spec.ts` was already failing before this change (it expects an Overview heading, "Every observation. One loop.", that is not in the committed code) and later fails on the ovitraps sample list, which the trap-visuals work restructured; the engineering-review assignment step it uses (`article` filter) was therefore not reached and is unverified against the board. The Assign button still assigns to the seeded inspector only. The board has no drag and drop by design, since each move is a role-gated action.

## Simulated drone trap pass and inbox (23 October 2026)

Added `POST /api/v1/drones/trap-passes` and `GET /api/v1/egg-analyses/inbox`, and a **Drone inbox** tab on Smart ovitraps. A pass makes one deterministic synthetic paddle image per reporting trap, runs the same egg-count model as photo uploads, and stores each result as an `egg_analyses` proposal with `source = DRONE_SIM` and a shared `capture_pass_id`. Responses are labelled `SIMULATED`. Offline or unserviced traps are skipped with a `DATA_UNAVAILABLE` reason. A repeated idempotency key returns the original results. Operator and coordinator can run a pass; reviewer and coordinator can confirm; the confirmed sample stays `SIMULATED`.

- Migration `009_egg_capture_source` adds `source` (existing rows become `UPLOAD`) and `capture_pass_id`. It is additive; its downgrade refuses to run.
- Tests: `services/api/tests/test_drone_capture.py` (6) and `apps/web/tests/drone-inbox.spec.ts`.
- Not real: no aircraft, no flight link, and the "photo" is generated, not captured. A pass returns all results in one request; the inbox only looks live because the page re-fetches every 5 seconds. Anything that can call the endpoint appears in the inbox the same way.

They fail the same way on the previous commit because the test modules share one database engine, and `test_loop.py` passes 9/9 when run alone. `test_allocation_benchmark.py` and `test_data_evaluation.py` fail to import `scripts.*` when run from `services/api`.
